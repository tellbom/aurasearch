# 5 万数据双写与 1 万请求压力测试报告

日期：2026-08-09

## 结论

- ES/Vespa 双写成功：业务 API 接收 50,000 条，最终 ES 50,000、Vespa 50,000、Outbox backlog 0。
- 返回准确性通过：ES、Vespa、RRF 各抽取 1,000 个唯一标记查询，稳定轮次均为 Top10 命中 100%、Top1 命中 100%。
- 10,000 请求、128 并发的 RRF 混合查询通过：10,000 个 HTTP 200，全部为真实 `Rrf` 响应，无降级，Top1 100%，362.408 req/s，P95 846.539 ms，P99 1,698.906 ms。
- 256 并发开始出现降级；512 并发绝大多数退化为 ES；瞬时 10,000 并发在当前单机 4 GiB Docker 环境失败，不能作为可承载配置。
- 本轮只走 HTTP API 验证业务链路，没有执行单元测试，也没有绕过 API 直接写 ES 或 Vespa。

## 环境与方法

- Docker Desktop：16 CPU、3.817 GiB 可用内存，Server 29.6.2。
- API：ASP.NET Core / .NET 6.0.25。
- Elasticsearch：7.17.25，IK 镜像 `aurasearch-elasticsearch-ik:7.17.25`，JVM Xmx 384 MiB。
- Vespa：8.721.11。
- API、ES、Vespa 位于独立的 `internal=true` Docker 网络；运行压测时不依赖互联网。
- 数据由 `tools/loadtest/api_load.py` 确定性生成，不复制外部数据。每条数据包含唯一 `lx...` 标记，可由测试端提前计算唯一预期 `newsId`。
- 灌入调用 `POST /api/v1/index/documents/batch`；查询调用 `POST /api/v1/search`；双写完成度调用 `GET /api/v1/operations/indexing-snapshot`。
- 准确性标准：唯一标记的预期 `newsId` 必须出现在 Top10，同时单独统计是否位于 Top1。RRF 轮次还检查 `searchMode=Rrf` 和 `degraded=false`，避免把 ES 降级返回误算成双引擎混合查询成功。

## 返回准确性

每个模式先预热，再执行 1,000 个固定种子的随机唯一标记查询，并发数 32。

| 模式 | HTTP 200 | Top10 | Top1 | 降级 | 吞吐 | P50 | P95 | P99 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| EsOnly | 1,000/1,000 | 100% | 100% | 0 | 571.395 req/s | 50.229 ms | 91.209 ms | 111.154 ms |
| VespaOnly | 1,000/1,000 | 100% | 100% | 0 | 292.047 req/s | 79.638 ms | 314.165 ms | 406.195 ms |
| Rrf | 1,000/1,000 | 100% | 100% | 0 | 287.660 req/s | 87.962 ms | 245.145 ms | 323.190 ms |

冷启动现象：ES 首轮曾出现 32/1,000 个 503；Vespa 顺序预热首个请求曾出现 503。完成预热和恢复后，上表稳定轮次全部成功。因此这些数据只证明稳定运行阶段，不代表冷启动可直接承载压力。

## 10,000 请求压力结果

所有轮次均查询唯一标记，并检查对应 `newsId`。

| 总请求 | 并发 | HTTP 200 | 真实 RRF | ES 降级 | Top1 | 吞吐 | P50 | P95 | P99 | 结论 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 10,000 | 128 | 10,000 | 10,000 | 0 | 100% | 362.408 req/s | 232.772 ms | 846.539 ms | 1,698.906 ms | 通过 |
| 10,000 | 256 | 10,000 | 9,550 | 450 | 100% | 326.954 req/s | 476.931 ms | 2,141.691 ms | 3,034.560 ms | 功能正确，但 4.5% 降级 |
| 10,000 | 512 | 9,984 | 859 | 9,125 | 99.84% | 233.526 req/s | 1,013.398 ms | 4,799.944 ms | 16,233.394 ms | 不通过 |
| 10,000 | 10,000 | 0 | 0 | 0 | 0% | 57.877 req/s* | 约 169 s* | 约 172 s* | 约 172 s* | 不通过 |

`10,000` 瞬时并发轮次共有 364 个 HTTP 503、9,636 个客户端传输失败，其中 8,475 个超时、1,161 个不完整 HTTP 响应。带星号的延迟和吞吐同时包含压测客户端事件循环/套接字饱和，不应解释为正常服务延迟。API 日志同时记录 Kestrel thread-pool starvation；容器未退出，恢复后数据仍为 50,000/50,000、backlog 0。

128 并发轮次是在重启专用压测容器、等待 ES/Vespa/API 就绪并完成 100 次顺序预热后独立重跑得到，未受上一轮残留请求队列影响。该轮最大延迟 1,983.722 ms，无传输错误。

## 资源观察

- 双写进行中：API 约 224.7 MiB，ES 约 630.6 MiB，Vespa 约 2.006 GiB。
- 128 并发轮次结束后：API 约 320.4 MiB，ES 约 585.2 MiB，Vespa 约 2.126 GiB。
- 10,000 瞬时并发后 API 曾升至约 463.1 MiB；Vespa CPU 峰值观察到约 124%。

这些结果只适用于本次 4 GiB、单 API、单 ES、单 Vespa 容器组合。128 是本轮验证出的稳定 RRF 并发点，不等同于生产容量上限；若要求 256 以上仍保持纯 RRF，需要增加容器内存、拆分节点/扩容，并重新压测。

## 复现工具

在能访问 API 的网络内执行：

```bash
python3 tools/loadtest/api_load.py --api-url http://dual-news-search:8080 ingest \
  --documents 50000 --batch-size 200 --parallel-batches 4

python3 tools/loadtest/api_load.py --api-url http://dual-news-search:8080 wait-sync \
  --documents 50000 --timeout 7200

python3 tools/loadtest/api_load.py --api-url http://dual-news-search:8080 accuracy \
  --mode Rrf --documents 50000 --samples 1000 --concurrency 32

python3 tools/loadtest/api_load.py --api-url http://dual-news-search:8080 load \
  --mode Rrf --documents 50000 --requests 10000 --concurrency 128 --timeout 45
```

工具只依赖 Python 标准库。若 API 只在 Docker 内网可见，可把仓库的 `tools/loadtest` 目录只读挂载到已有 Python 镜像后，在同一 Docker 网络内执行。
